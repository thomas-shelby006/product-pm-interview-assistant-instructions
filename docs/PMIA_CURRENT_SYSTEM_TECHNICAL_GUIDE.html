What the system is

PMIA is a Windows-local interview operations system. It does not call a provider API and it does not send transcript data to a separate server. It coordinates two managed provider tabs—one acting as the question source and one acting as the answer workspace—through a Microsoft Edge extension. AutoHotkey provides the native launch and window-management shell; the extension owns browser observation, durable delivery, batching, proof, recovery, and the live dashboard.

What you must do for normal use

You do not need to run a build, packaging script, archive script, or deployment script every time. Start the AutoHotkey launcher, run Session Studio Preflight, provide session context when needed, and launch the interview. Scripts are maintenance and verification tools, not part of the normal interview ritual.

Section 2

What changed, and what the system gained

The current system grew through two architectural transitions. The first replaced a Tampermonkey userscript bridge and coordinate-driven Edge Beta launcher with a proper Manifest V3 extension. The second expanded the early extension runtime into a lossless, observable, restart-aware operations platform.

Tampermonkey predecessor

A document-idle userscript ran inside ChatGPT, inferred sender or receiver role from a URL parameter, stored coordination flags in Web Storage, maintained small fixed buffers, and depended on a local update server. AutoHotkey used Edge Beta and screen coordinates for some controls.

Earlier extension deployment

The 0.6.1 runtime already had a service worker, provider adapters, provisional previews, profile-aware preflight, duplicate-safe acknowledgement, and rendered-turn evidence. It established the correct platform but had a much smaller control plane and no full Runtime Pilot operating surface.

Current 0.10.4 system

The current runtime adds durable sender ownership, a lossless delivery ledger, active and next batch separation, pause and catch-up, adaptive turn coordination, direct role ports, recovery budgets, alarms, state integrity, rich diagnostics, accessibility, and a full live operations dashboard.

Reliability gain

The old bridge could treat “a click happened” or “the composer cleared” as progress. The current system does not call a question delivered until a new matching provider-rendered user turn is observed. A sender final remains protected until another component has durably accepted ownership.

Efficiency gain

Provisional transcript text uses a disposable, coalesced preview lane, while authoritative finals use the slower durable lane. Direct runtime ports, sequence feedback, batching, cached dashboard views, and event-driven observation reduce unnecessary storage reads and polling.

Operator gain

The Runtime Pilot Dashboard turns hidden state into actionable state. It shows inbox age, outbox pressure, proof status, current and next batch ownership, pause state, recovery progress, transport health, readiness, storage pressure, and safe repair actions.

Maintenance gain

Provider-specific DOM knowledge is isolated in adapters and observation modules instead of being mixed into one userscript. Shared policies and state machines are independently tested, and a complete local gate checks JavaScript reachability plus both AutoHotkey programs.

The current architecture is not simply “more features.” Its central improvement is explicit ownership. Every meaningful transition—observed, persisted, staged, submitted, rendered, answered, exported, ended—has a component that owns it and evidence that proves it.

Which extension does what

The Edge profile contains PMIA and Browser Evidence Capture registrations. They serve different systems and should not be treated as alternative versions of the same application.

PM Interview Dual-Provider Runtime

Purpose: run the interview workflow. It observes ChatGPT and Claude, transports questions, owns delivery state, controls batching, verifies provider-rendered submission, tracks answer state, exposes the Runtime Pilot Dashboard, and exports the managed session.

Scope: only ChatGPT, ChatGPT’s legacy host, and Claude. Its permissions are storage, alarms, tabs, and windows. It does not request debugger access and it is not a general browser automation tool.

Browser Evidence Capture legacy loader card

Edge retains a registration whose path name contains BrowserEvidenceCapture-1.7.3 and whose card can display cached 1.7.8 behavior. The files currently present at that path contain the 5.3.0 manifest. This is a legacy loader anchor with a distinct extension ID.

Browser Evidence Capture 5.3.0 card

A second registration points to the explicit 5.3.0 installation directory. It has the same current manifest description and broad browser-control permission set as the files behind the older loader path.

Browser Evidence Capture is infrastructure for browser control, screenshots, semantic evidence, bounded workflows, and diagnostics. It requests permissions such as debugger, scripting, sidePanel, downloads, offscreen, and broad HTTP/HTTPS host access because it must inspect many applications. PMIA is the application being operated and tested. PMIA does not depend on Browser Evidence Capture for normal daily use.

Finding for later BEC research: the two BEC registrations are different Edge identities and paths, but both paths currently expose the same 5.3.0 manifest. The visible version discrepancy is therefore registration/cache history, not two independent current codebases. This PMIA cleanup intentionally leaves both untouched.

Architecture and ownership

The system deliberately separates native lifecycle control, browser-page observation, durable coordination, and operator presentation. Each boundary exists because the failure modes are different.

Browser data and state pathNative control or explicit operator actionOperator projection of authoritative state

Control plane and data plane

The data plane carries preview text, authoritative question envelopes, sequence feedback, batch membership, rendered proof, and answer lifecycle signals. The control plane carries registration, pause, catch-up, hold, submit-now, interrupt confirmation, repair, self-test, export, and shutdown commands. Keeping them separate prevents a dashboard button or telemetry event from becoming accidental delivery truth.

The full journey of one question

This is the normal path from the question-source page to a proven receiver turn. The system can recover or pause at several stages, but it never skips the ownership transition.

Provider observation begins with a semantic adapter

The sender runtime selects the ChatGPT or Claude adapter. It observes the provider’s real composer, voice/transcript surface, submitted turns, and generation controls. Claude also has a MAIN-world signal script for provider events that are not visible from the isolated extension world.

Provisional text travels on a disposable lane

Interim transcript changes are normalized, deduplicated, sequenced within the current page lifetime, and coalesced by the preview scheduler. The service worker routes them to the receiver for composer prefill. Preview text never enters the lossless ledger and can be dropped or replaced without losing an authoritative question.

An authoritative final receives a stable identity

When provider-specific finalization evidence is strong enough, the sender constructs an envelope with session identity, provider, role, sequence, text, source metadata, and a deterministic fingerprint. A repeated final with the same identity is acknowledged as a duplicate rather than submitted again.

The sender outbox prevents the first loss window

The final enters browser-session storage before forwarding. The sender does not delete its copy merely because a message was sent. It removes the entry only after the service worker replies that durable ownership was accepted. On reload, the outbox restores and replays in sequence order.

The service worker becomes the authoritative owner

The Runtime Pilot controller checks duplicate identity, ordering, pause mode, queue-only policy, storage pressure, route readiness, and current recovery state. It persists the delivery ledger and returns a specific acknowledgement. If the receiver is unavailable, the ledger retains the final rather than treating transport failure as delivery failure.

The receiver admits sequence before batch ownership

The receiver sequence buffer blocks gaps and returns exact acknowledgements and negative acknowledgements. Flow-control credits prevent unbounded staging. Once ordering is safe, the receiver batch runtime places the final into the active batch when idle or the mutable next batch while an answer is in progress.

Batch composition preserves every question

A single waiting question is submitted without artificial wrapping. Multiple waiting questions are composed into one prompt that retains each question and marks the latest as highest priority. The active batch is immutable once submitted; new arrivals update only the next batch, so a currently generating answer is not silently changed.

Composer ownership is verified before submission

The composer arbiter distinguishes the runtime’s own preview or final draft from a user-edited draft. It will not overwrite a conflicting manual draft. Submission uses provider-specific semantic controls, not screen coordinates. If the provider clears the composer but fails to render a user turn, one bounded retry is allowed only when generation has not started and no newer draft has appeared.

A rendered provider turn is the delivery proof

The receiver compares the post-submit conversation against a pre-submit baseline. The batch is proven only when a newly rendered provider user message matches the frozen batch fingerprint and membership. A click, cleared textarea, background acknowledgement, or telemetry event cannot substitute for this proof.

Answer observation and settlement complete the active batch

The answer orchestrator tracks waiting, streaming, complete, no-response, timeout, and cancellation states using provider generation evidence and text stability. Settlement is idempotent: terminal callbacks and promises converge on one owner. When the active answer completes, the next protected batch may submit according to hold and auto-submit policy.

Dashboard, export, and shutdown use the same truth

The dashboard receives snapshots and command results from the Runtime Pilot controller. Export asks both managed roles for a safe schema 2.1 record. End-session checks for unresolved finals, outbox entries, and actionable coordination before clearing registry, ledger, batch, dashboard, role logs, and AutoHotkey in-memory context.

The reliability model

PMIA’s reliability comes from invariants that are enforced across modules, not from one retry loop.

  • Preview is never truth. Interim text can be overwritten, coalesced, or lost without changing the authoritative ledger.
  • Every final has one durable owner. The sender retains ownership until the service worker persists it; the ledger retains it until rendered proof or explicit archive.
  • Order is explicit. Sequence gates, contiguous buffers, acknowledgements, and negative acknowledgements make gaps visible and recoverable.
  • Duplicate identity is idempotent. Replays acknowledge the same final without creating another provider turn.
  • The active answer is non-preemptive by default. New questions accumulate in the next batch. Only a confirmed explicit interruption can stop generation.
  • Submission is not delivery. Provider-rendered proof is mandatory, and restart reconciliation searches existing rendered turns before replay.
  • Recovery is bounded. Automatic repairs use rolling budgets, cooldowns, reason codes, and alarms. Manual repair remains available without creating an infinite loop.
  • State is sealed and migratable. Integrity digests, previous-state recovery, schema migration, commit journals, and quarantine protect against partial or future state.
  • Private content is minimized. Active role logs use session storage; support bundles and dashboard snapshots exclude Resume, job description, prompt, answer, credentials, and provider URLs.
  • Shutdown is guarded. Unresolved finals, sender outbox state, and actionable coordination must be cleared or explicitly archived before clean end.

Alternatives considered

The chosen architecture is not the only way to build the workflow. It is the best fit for local, low-latency, provider-page operation without provider APIs or a remote service.

Keep Tampermonkey plus AutoHotkey

This was the fastest prototype and required little packaging. It was rejected as the long-term design because one userscript combined observation, transport, buffering, role state, and logging; Web Storage became coordination state; local update serving was another dependency; and browser restart, sequence gaps, proof, and multi-surface diagnostics were difficult to make authoritative.

Build an extension with no AutoHotkey shell

A browser-only extension would be more portable and reduce the Windows dependency. It was not selected because PMIA needs predictable multi-window launch, exact native layout, profile selection, hotkeys, process ownership, Review Studio launch, and safe closure of only the managed windows.

Build a desktop application with native messaging

A native app could own persistence, browser automation, updates, and richer diagnostics. The cost would be an installer, native-messaging host, signing and update infrastructure, a larger security boundary, and more code than the current local use case requires.

Use a server or provider APIs

A cloud relay could centralize sessions and support multiple devices. It would add network latency, authentication, operational cost, private transcript handling, and dependence on provider APIs that do not mirror the live voice/composer experience.

Publish through the Edge Add-ons store

A store build would provide a stable extension ID and managed updates. It is a reasonable future option, but it requires packaging, signing, review, privacy disclosures, and release-channel discipline. Direct unpacked loading is appropriate for a single-user, rapidly evolving local tool.

Keep a separate generated deployment folder

A sealed package can help formal distribution and rollback. On this machine it created two current-looking trees, path aliases, package tests, inventory files, archives, and synchronization work. Direct-source loading is simpler because Git already provides history, review, and recovery.

Trade-offs accepted

DOM integration instead of provider APIs

The live experience is available with no API keys and matches the user’s browser session. The trade-off is selector and behavior drift when ChatGPT or Claude changes. Adapters, capability probation, selector fallbacks, and isolated smoke evidence reduce—not eliminate—that risk.

Manifest V3 service-worker lifecycle

An event-driven service worker is resource-efficient and aligns with current extension policy. It can stop after inactivity, so global variables cannot be trusted. PMIA persists durable state, rehydrates alarms, restores ports, and reconciles on startup.

Session storage for privacy

Session storage keeps active state in memory and clears it on extension reload, disable, update, or browser restart. That limits long-lived private data, but true restart continuity must come from explicit sealed state and reconciliation rather than unlimited local transcript storage.

AutoHotkey for native control

AutoHotkey gives precise Windows layout, hotkeys, profile launch, and process ownership with a small code footprint. The application is therefore Windows-specific and depends on AutoHotkey v2 being installed.

Rich observability

The dashboard, state models, diagnostics, recovery centers, and tests make failures explainable and controllable. They also increase module count and learning surface. Architecture-boundary and growth-budget tests prevent the observability layer from becoming a second uncontrolled application core.

Direct-source unpacked loading

There is now one current tree and no packaging synchronization. The trade-off is manual Reload after code changes, Developer mode, and a path-derived extension ID. Git history replaces local archive folders as the recovery mechanism.

How to operate the application

Normal interview day

  1. Run runtime\Final_2_Window_Extension.ahk.
  2. Confirm the selected Edge profile in Session Studio.
  3. Select the sender and receiver providers, then enter Resume, job description, and optional session metadata.
  4. Select Preflight. Continue only when PMIA 0.10.4 is registered from the expected repository path.
  5. Select Launch Interview. The sender reaches readiness before the receiver and dashboard complete their registration.
  6. Use the Runtime Pilot Dashboard for live health, pause, catch-up, hold, submit-now, diagnostics, repair, layout, export, and end-session.
  7. Use Alt+Delete to end the managed session. Use Alt+Shift+E when a paired review export is required.

What happens automatically

Once the extension is loaded and the launcher starts, registration, preview transport, final persistence, sequence feedback, batching, rendered proof, answer observation, dashboard updates, alarm rehydration, recovery attempts, and session cleanup are automatic. The user intervenes only for session context, explicit operating choices, a repair that exceeds the automatic budget, or an extension Reload after source changes.

How to maintain it going forward

Before changing code

Work from the canonical repository on a short-lived branch or isolated worktree. Keep main clean. Do not create another copy under Documents. Private session data belongs under .local, not in commits.

After changing code

Run the complete validator. When it passes, open edge://extensions and select Reload on the PMIA card. Start fresh managed provider tabs and run Preflight. A source edit is not live in an already running extension until Reload occurs.

When a provider UI changes

Start with the adapter and observation evidence. Update the smallest provider-specific selector or signal contract, add a regression, run the focused adapter tests, then the complete gate and isolated browser smoke. Do not patch the dashboard or ledger to compensate for a DOM-observation failure.

When delivery appears stuck

Use Check Live, the sender outbox, Gap Watch, proof inspector, batch state, and recovery progress to locate the owner. A persisted final is not lost merely because the answer is delayed. Use Repair only after reading the named reason.

Versioning and recovery

Do not create ZIP backups or archive directories for each change. Commit meaningful milestones. Git history and the existing private remote are the recovery system. A release tag is optional only when a stable milestone must be named.

Session evidence

The private tracker is a separate Git repository under .local\session-tracker. Review its status before pushing real sessions. Application code and interview evidence must remain separate because their privacy, retention, and review cycles differ.

Pending from your side after this consolidation: nothing is required for the application to keep working beyond normal launch and session context. Developer mode must remain enabled for the unpacked extension, and you must remain signed in to the selected provider pages. Run the validator and Reload only after source changes. The two Browser Evidence Capture cards remain a separate cleanup decision.
