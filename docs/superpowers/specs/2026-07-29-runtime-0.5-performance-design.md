# PMIA Runtime 0.5 Performance Design

## Goal

Reduce sender-to-receiver latency and eliminate avoidable hot-path blocking while preserving authoritative provider boundaries, latest-question superseding, durable final delivery, and the existing rollback runtime.

## Evidence

- Browser Evidence Capture 1.5.0 reported two connected tabs and correctly rejected stale session IDs after relay reconnect.
- Claude's live page exposes `div[data-testid="chat-input"]`, a `Press and hold to record` control, and a `Use voice mode` control. No active loading indicator or material console error was present.
- The connected Claude event window contained 113 events; the current ChatGPT window contained 77 events. Neither reconnect window contained a new in-progress transcript, so protocol rules continue to rely on the previously captured Claude `transcript_interim`, `user_input_end`, human `message_complete`, interruption/reset, and assistant `message_stop` evidence.
- ChatGPT's live page showed substantial main-thread contention and many long tasks. PMIA should therefore avoid synchronous storage and avoid unnecessary DOM writes on the transcript hot path.
- Current code performs a synchronous `sessionStorage.setItem` for every disposable preview.
- Current receiver code waits for durable logging before entering delivery and always sleeps 60 ms after setting the composer.

## Selected Architecture

Retain the extension-only two-lane architecture.

### Preview lane

- Provisional text remains disposable and never enters the durable registry or recovery queue.
- Preview sequence is page-lifetime in-memory state only.
- Same-task preview bursts are collapsed to the latest candidate with `queueMicrotask`; there is no timer or animation-frame delay.
- Receiver preview updates remain non-submitting and non-interrupting.
- Receiver preview state is bounded and committed turns are removed.

### Final lane

- Service-worker sequence acceptance and latest-only queueing remain durable.
- Receiver submission happens before session-log persistence.
- Composer submission is attempted immediately after the provider input event.
- If the send control is not ready, a bounded readiness retry waits at most two short checks; there is no unconditional 60 ms delay.
- Receiver acknowledgement remains explicit. A final is accepted only after submission succeeds.

### Provider state

- Claude protocol signals remain authoritative for native voice interim/final boundaries.
- DOM stable-tail fallback is prohibited while voice or recording is active.
- Adapters recognize both full voice mode and press-and-hold recording controls/states.
- Non-voice fallback is reduced from 1200 ms to 650 ms only for a submitted tail with an empty composer and no active voice/recording state.
- Assistant-successor finalization remains the preferred DOM boundary.

### Telemetry

- Logging and export remain durable but cannot delay final submission.
- A receiver log records the final only after successful submission, including measured delivery elapsed time.
- No raw Browser Evidence event dump is committed.

## Non-goals

- No local daemon or new IPC layer.
- No provider API calls, cookie access, or undocumented request replay.
- No changes to `Final_2_Window_Fixed.ahk`, Tampermonkey scripts, historical archives, old ZIP files, or other legacy assets.
- No dependency installation.

## Failure handling

- Missing receiver: disposable preview drops; durable final queues latest-only.
- Stale or duplicate final: rejected by sequence gates.
- Provider send control not ready: bounded retry, then explicit rejection so the service worker retains latest pending work.
- Receiver already generating: stop and wait for idle using the existing bounded supersede behavior.
- Extension reload: durable final sequence/registry survives; previews restart from in-memory sequence zero and are valid only for the new page lifetime.

## Acceptance criteria

1. No preview path performs browser storage writes.
2. Multiple previews queued in one JavaScript task deliver only the newest candidate.
3. Final submission occurs before receiver log persistence begins.
4. A provider-ready composer submits without the old fixed 60 ms sleep.
5. A temporarily disabled send control receives a bounded retry and then submits or rejects cleanly.
6. Claude press-and-hold recording blocks stable-tail fallback.
7. Non-voice fallback uses 650 ms only when the composer is empty and voice is inactive.
8. Preview revision memory remains bounded and committed turns are cleared.
9. All existing behavior and release validation remain green.
10. Only files created or modified for runtime 0.5 are cleaned; older files remain untouched.
