# PMIA 0.10 Control-Plane Coherence, Live Features, and Hardening Design

## Objective

Upgrade the verified PMIA 0.9 runtime into PMIA 0.10 by fixing current control-plane defects, introducing ten substantial live-interview user features, and then completing thirty focused bug-fixing cycles against the expanded system.

The lossless delivery ledger, sender outbox, sequence admission, protected receiver batches, rendered proof, transport fallback, and session-only privacy model remain authoritative. The work improves command reachability, operator safety, live navigation, lifecycle reliability, performance, evidence, and documentation without adding a second transport, state store, or recovery owner.

## Binding constraints

- No non-duplicate Window 1 final may be lost.
- Window 2 accumulation and latest-question priority remain exact.
- Provider-rendered user turns remain the only authoritative submission proof.
- Normal Edge must not be foregrounded or disturbed.
- Work stays in the isolated improvement worktree; no push, merge, tag, or installed-extension replacement.
- Sensitive interview content remains in session-only state and is excluded from support/release evidence.
- Tests are authored with development work and executed only at the planned consolidated gates.
- The standalone technical HTML is updated once, after the complete 40-cycle extension is implemented and verified.

## Confirmed baseline defects

1. `compact_proven` and `retry_outbox` are visible and handled by the controller but rejected by the dashboard protocol.
2. The dashboard contains two elements with the ID `openShortcutHelp`.
3. The release-evidence builder does not require or preserve `productionUiOk`.
4. The Decision Center exposes executable defaults for no-response and draft-conflict choices that require explicit operator intent.
5. Active documentation and setup surfaces still describe PMIA 0.7 or 0.8 while the verified runtime is 0.9.
6. Command knowledge is duplicated across markup, protocol, controller dispatch, availability logic, and tests.
## Architecture decision

Use a generated control-plane coherence layer around the existing runtime.

A shared command registry becomes the only source of truth for command ID, label, category, risk, confirmation mode, required payload, controller owner, availability projection, and whether the action executes, navigates to a choice, or only inspects state. Dashboard protocol normalization, command palette/search, visible controls, and reachability tests consume this registry.

The registry does not perform runtime mutations. Existing controller cases and content-runtime commands remain the execution owners. The registry only validates and describes the route to those owners.

Consequential decisions use three explicit action modes:

- `execute`: a deterministic, reversible command can run directly.
- `choose`: the Pilot navigates to the owning decision surface and requires the operator to select an option.
- `inspect`: the Pilot opens the relevant evidence without mutation.

No-response and draft-conflict decisions are always `choose` actions. The Decision Center may rank them, but it cannot silently select Continue, Retry, Restore, Merge, or Keep Manual.

## PMIA 0.10 coherence foundation

### Command registry and reachability

- Add `shared/operator-command-registry.js` as the canonical metadata registry.
- Generate the dashboard protocol allow-list from registered commands.
- Keep payload normalization in the protocol, with registry-declared payload schemas and command-specific sanitizers.
- Add a controller-owner map and a static/runtime audit proving every visible command reaches one controller owner.
- Reject duplicate command IDs, duplicate DOM IDs, missing protocol routes, missing handlers, unsupported risk values, and unavailable commands without reasons.
- Repair the `compact_proven` and `retry_outbox` routes through the shared registry.

### Decision safety

- Replace executable defaults for ambiguous decisions with navigate-to-choice actions.
- Preserve operator selections through reconnects and worker suspension without inventing a default.
- Record only choice type, selected option, timestamps, and result metadata; never record question or answer text in decision history.

### Release-evidence closure

- Require `productionUiOk` in deterministic release evidence and handoff readiness.
- Preserve Production-view desktop, 320-pixel, 280-pixel, print, accessibility, and control evidence in the manifest.
- Fail evidence generation when Pilot or Production controls are visible but unreachable.
- Include command-registry digest and control-reachability audit in the release manifest.

### Version/documentation alignment

- Promote active runtime and documentation to PMIA 0.10.0 candidate.
- Rewrite active context, status, setup, installation, and README release sections.
- Keep historical migration/design files unchanged and clearly historical.
## Ten user-facing live-interview cycles

Each cycle must produce a visible operator capability, one bounded owner, and a regression contract.

1. **Persistent Live Action Dock** — a view-independent footer showing current answer state, protected waiting count, primary decision, containment status, and one safe action.
2. **Policy Impact Preview** — before applying Safe/Balanced/Fast profiles or containment overrides, show affected controls, protected-question count, provider-write change, post-answer behavior, reversibility, and confirmation risk.
3. **Choice Workspace** — one focused surface for no-response, draft conflict, interruption, session end, and other multi-option decisions; preserves the exact unresolved choice across reconnects.
4. **Interview Milestone Navigator** — phase-aware landmarks for setup, ready, active segments, pause, recovery, debrief, and end; includes a Back-to-live action without altering delivery state.
5. **Operator Inbox Triage Board** — saved metadata-only views for urgent, deferred, pinned, follow-up, stale, and proof-pending questions; ordering remains sequence-safe.
6. **Provider Route Doctor** — explains current sender/receiver adapter capability, selector evidence, write safety, send-control readiness, and the exact repair action for the active route.
7. **Recovery Runbook Console** — visualizes the current recovery step, completed checks, retry budget, next deadline, and the reason an automatic action is or is not allowed.
8. **Session Command History and Undo** — searchable command journal with result, duration, replay count, reversible metadata undo, and navigation to the affected surface.
9. **Live Performance and Backlog Forecast** — predicts proof delay and catch-up time, distinguishes provider delay from internal backlog, and warns before a live interview becomes operationally unsafe.
10. **Preflight and Handoff Wizard** — one guided flow for starting a mock interview and one guided flow for ending/exporting it, reusing self-test, readiness, checkpoint, privacy, cleanup, and release evidence owners.

## Thirty post-feature bug-fixing cycles

The bug phase begins only after the ten feature cycles are source-complete. Each cycle must fix a confirmed defect, invariant violation, or reproducible failure mode; speculative refactors are excluded.

### Control-plane and decision integrity — Cycles 1–6

1. Command registry/protocol/controller parity under added and removed commands.
2. Duplicate IDs, stale element references, and disconnected event listeners.
3. Payload schema, sanitization, and choice-state replay after reconnect.
4. Operation Guard concurrency, timeout, duplicate result, and cancellation behavior.
5. Decision Center ranking, navigation targets, and explicit-choice enforcement.
6. Shortcut, command palette, Action Dock, and dialog focus consistency.

### Runtime lifecycle and ownership — Cycles 7–12

7. Service-worker suspension during commands, decisions, and policy preview.
8. Content-runtime reload, BFCache restore, prerender, freeze, and discard recovery.
9. Duplicate runtime injection, registration lease expiry, and owner election.
10. Dashboard disconnect/reconnect with pending commands and unresolved choices.
11. Alarm rehydration, overdue deadlines, and stale-generation rejection.
12. Safe shutdown, crash resume, and incomplete cleanup continuation.

### Lossless transport and receiver mechanics — Cycles 13–18

13. Sender outbox write failure, replay order, retry intent, and duplicate acknowledgement.
14. Ledger index drift, tombstones, compaction horizon, and exact member proof.
15. Out-of-order sequence gaps, NACK/retry, and reconnect continuity.
16. Receiver credit, backpressure, batch partitioning, starvation, and fairness.
17. No-response, pause-after-answer, drain, submit-on-idle, and interruption races.
18. Manual composer conflict and provider-rendered proof under route changes.

### Provider, storage, and performance — Cycles 19–24

19. Selector drift, capability probation, hidden-window scheduler, and send-control mounting.
20. Provider route changes during active/next protected batches.
21. Storage pressure, failed transactional writes, rollback, and safe compaction.
22. Snapshot delta, section cache, render coalescing, and idle-work correctness.
23. Large ledger/command/timeline load, virtual-list boundaries, and memory budgets.
24. SLO forecasting, clock monotonicity, timeout adaptation, and false escalation.

### Accessibility, evidence, and release — Cycles 25–30

25. Keyboard-only operation, roving focus, dialog return focus, and gesture-token expiry.
26. Reduced motion, text scaling, contrast, live-region deduplication, and narrow layouts.
27. Support-bundle privacy, release-manifest privacy, and content-leak detection.
28. Pilot/Production desktop, 320-pixel, 280-pixel, and print control reachability.
29. Isolated-browser source submission, three-proof delivery, transport drill, and cleanup reliability.
30. Active-document version alignment, architecture budgets, clean-tree handoff, and deterministic evidence reproduction.
## Data and command flow

1. The Pilot renders command metadata from the shared registry and current authoritative snapshot.
2. A user action is normalized by the dashboard protocol using the registry-declared payload contract.
3. The controller dispatches to the existing owner and records result metadata in the bounded command journal.
4. Consequential ambiguous actions navigate to the Choice Workspace and do not execute until a valid explicit option is submitted.
5. Runtime state changes persist through the existing session store and are projected back through full snapshot, semantic delta, or heartbeat lanes.
6. Release evidence audits the same registry, visible controls, controller owners, browser evidence, privacy, and cleanup state.

The Action Dock is a projection, not a state owner. It derives its label and action from the Decision Center, live answer state, inbox, containment, and registry availability. It cannot directly mutate ledger, batching, provider, or recovery state.

## Error handling

- Unknown, unavailable, malformed, or ownerless commands fail closed with a reason code and owning surface.
- A choice-required action cannot fall back to an implicit option on timeout, reconnect, or missing UI.
- Policy previews expire when the underlying snapshot changes; confirmation requires a matching snapshot fingerprint.
- Failed commands preserve pending delivery and choice state; retries use the existing command-result journal.
- Release evidence fails closed when command reachability, Production UI, privacy, cleanup, or exact-commit identity is incomplete.
- Provider/transient browser failures remain separate from transport proof and are reported as external limitations when evidence supports that classification.

## Test and verification strategy

Development uses test-first contracts, with executable runs deferred to the agreed gates.

### Foundation gate

Run focused command-registry, protocol, controller, dashboard, decision-safety, evidence, and documentation tests after the PMIA 0.10 coherence foundation is source-complete.

### Feature gate

After all ten user-facing cycles are source-complete, run their focused suites plus the complete repository validator. Browser verification must exercise the Action Dock, Choice Workspace, policy preview, keyboard flow, route doctor, recovery console, and start/end wizards without disturbing normal Edge.

### Bug campaign gate

After all thirty bug cycles are complete, run the entire automated validator, isolated Edge three-proof smoke, expanded no-content drill, lifecycle/restart matrix, privacy audit, responsive/print proof, deterministic release evidence, and cleanup verification.

### Final artifact gate

Update the standalone technical HTML only from the final verified PMIA 0.10 architecture. The artifact must be self-contained, offline, code-free, technically deep, and explain the current implementation through diagrams, state machines, sequence flows, interactive feature maps, failure paths, and evidence.

## Acceptance criteria

- Every visible or generated command has exactly one registry entry, one protocol route, and one controller owner.
- `compact_proven` and `retry_outbox` execute through the normal dashboard route.
- The dashboard contains no duplicate IDs and every interactive control is reachable by keyboard.
- No-response and draft conflict require explicit operator choice.
- Policy application cannot execute from stale preview evidence.
- The Action Dock remains accurate across all Pilot views, reconnects, suspension, and session end.
- All ten feature cycles are visible and usable in isolated-browser evidence.
- All thirty bug cycles have a reproduced defect, owning fix, and regression contract.
- Release evidence requires both Pilot and Production UI gates.
- Active runtime/setup/status documentation consistently identifies PMIA 0.10.0 candidate.
- Candidate and original worktrees are clean; no push, merge, or tag occurs.

## Non-goals

- No large prompt redesign or interview-content intelligence.
- No replacement of the lossless ledger, provider adapters, transport hub, or session store.
- No automatic execution of ambiguous human decisions.
- No background tab activation or focus theft.
- No external relay, cloud persistence, remote analytics, or additional dependency framework.
- No unrelated repository cleanup.
