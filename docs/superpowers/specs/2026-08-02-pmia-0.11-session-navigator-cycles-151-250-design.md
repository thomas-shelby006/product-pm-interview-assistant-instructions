# PMIA 0.11 Session Navigator and Hardening Design

**Date:** 2026-08-02  
**Scope:** Cycles 151–250  
**HTML:** held until implementation, automated validation, isolated Edge proof, evidence and cleanup are complete.

## Objective

Add one persistent live-session navigation surface that reduces operator cognitive load without creating a second ledger, transport, recovery or provider-writing owner. Then harden the completed feature set under lifecycle, transport, provider, storage, load, accessibility and release stress.

## Architecture decision

The Session Navigator is a snapshot-derived dashboard surface. It reads the existing ledger, batch, answer, incident, marker, trace, live-session and production-control state. Only bookmarks, competency goals and workspace presets become new persisted operator metadata. Search query, selected local tab, previews and scenario playback remain dashboard-local.

### Persisted owner

`RuntimePilotState.sessionNavigator` owns bounded bookmarks, competency targets, question coverage tags and workspace presets. It uses extension session storage, participates in schema migration and integrity repair, and never stores answer text, setup context, credentials or raw provider URLs.

### Derived owners

Dedicated pure models derive search results, question threads, pace, handoff readiness, scenario comparison, goal coverage and debrief output. `render-session-navigator.js` owns rendering. `session-navigator-controller.js` owns local tabs, keyboard movement and search state. Existing commands remain authoritative for question metadata, markers, receiver policy, recovery and window navigation.

### User-facing views

Now, Search, Threads, Pace, Handoff, Workspaces, Scenarios, Bookmarks, Goals and Debrief. All panels are preloaded, keyboard accessible, responsive at 320 and 280 CSS pixels, printable, and content-free in release evidence.

## Constraints

- No new transport, ledger, outbox, recovery engine or provider adapter.
- No automatic provider switching or focus changes.
- No large prompt work.
- No transcript content in support, release or handoff evidence.
- Tests are written with source changes and executed after source completion.
- Original checkout remains untouched; no push, merge or tag.

## Research basis

Chrome MV3 service workers are non-persistent, so reconstructible session state, alarms and message-driven ownership remain mandatory. Side panels can remain open across tab navigation but may open only from a user gesture; Navigator therefore remains in the existing Pilot and may expose an optional gesture-triggered side-panel route later. WAI-ARIA tab, toolbar and dialog patterns require roving focus, visible selected state, bounded tab stops and focus containment for consequential confirmations. Recent interview-assistant research emphasizes structured multi-turn practice, evidence-linked feedback and real-time cognitive support; the design adds navigation and coverage support without moving interview content into release evidence.

## Execution amendment — system architecture and lifecycle

The latest approved scope adds these hard requirements to Cycles 151–250:

- one project runtime instance; a second launch activates the existing Studio instead of replacing an active session;
- a normalized browser runtime configuration with Edge as the default, Chrome-compatible executable/profile support, reviewed low-latency flags and browser-specific internal URLs;
- one managed-process/window ownership journal so relaunch and shutdown close only PMIA-created windows/processes for the selected session;
- no automatic foreground activation during launch, repair or cleanup; focus changes require an explicit operator action;
- one phase-oriented Pilot workflow: pre-launch, launch, live mock, export, review and graceful shutdown;
- one post-interview transaction covering role export, export verification, Review Studio handoff, safe end preparation, exact managed-window cleanup and AHK exit;
- complete Pilot access to launch health, browser/profile state, export/review status, managed-window ownership and shutdown actions;
- route verification for ChatGPT→ChatGPT, ChatGPT→Claude, Claude→ChatGPT and Claude→Claude without repeating evidence already proven on the same unchanged owner;
- removal of dead production modules and source-shape-only tests; new tests must exercise real behavior and fail when the production owner regresses;
- the standalone HTML report remains explicitly out of scope for this run.

Cycle mapping: Navigator and phase workflow are delivered in 151–200; command/snapshot/transport/provider/state/performance hardening remains 201–250. Single-instance, browser abstraction, managed ownership, export/review/shutdown and code/test cleanup are mandatory cross-cutting acceptance work inside Blocks 236–250.
