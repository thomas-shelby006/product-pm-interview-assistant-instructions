Executive summary

PMIA 0.12 is no longer a large reliability dashboard wrapped around two answer windows. It is a small three-window production runtime with one direct delivery path and one terminal success rule: the exact interviewer turn must be rendered as a provider user turn in every configured answer lane.

Architecture: one path, three windows

Window 1 · Source

Observe only newly rendered user turns. Baseline history once. No answer analytics, batch planner, or persistence gate before forwarding.

→
MV3 service worker

Long-lived ports. One concurrent fan-out. Independent per-role FIFO queues. Persist only unresolved role failures.

→
Window 2 + Window 3

Equal production lanes. Provider-native write → verified composer → real submit → exact rendered-turn proof.

Hot-path invariant: W1 rendered turn → port → concurrent W2/W3 fan-out → role FIFO → provider write → submit → rendered proof.

AutoHotkey is not part of this live path. The active AHK file is only an optional Studio bootstrap. Review, export, markers, display preferences, window tools, and answer-size metrics observe the runtime from the side and cannot delay a question.

Features deliberately not imported

These outcomes were reviewed against interview value, hot-path cost, continuous cost, state/privacy cost, and debugging burden. They remain retired because restoring them would recreate the failure-prone 0.11 control plane.

Runtime Pilot / Reliability Center / Operations LabDropCompact status + bounded trace + export. Operator dashboards do not belong in the interview hot path.
Global question sequence / gap recoveryDropLong-lived port ordering + independent role FIFOs remove the missing-sequence class of failures.

Scenario coach / competency goal engineDropInterview coaching remains in the project prompt/content layer, not transport runtime.
Mic / scroll automationDropProvider-native UI behavior is less fragile.
Forced interrupt / forced submit / hold-after-answerDropPause/Gather + role FIFO preserve lossless, predictable delivery.
Crash-resume orchestration state machineDropBounded session metadata + port reconnect is enough for the simplified runtime.
Selection rule: preserve the user outcome, not the old implementation. If a feature needs another state machine, timer loop, ledger, or delivery owner, it must prove enough user value to justify that complexity.

Current provider compatibility fixes

ChatGPT

  • Current ProseMirror no longer depends on the previous node.editor API. PMIA now synchronizes native insertion with ChatGPT’s React before-input state.
  • If a real Send button exists, PMIA uses it. If current ChatGPT exposes no Send button, PMIA uses the exact composer’s nearest form requestSubmit(); this was live-proven to create a real conversation and rendered user turn.
  • W1 startup removes an old PMIA setup draft only when the current composer begins with the exact known PMIA setup prefix. Arbitrary user drafts are left untouched.
  • Rendered proof uses current semantic user-turn selectors, with maintained fallbacks for older markup.

Claude

  • PMIA writes through Claude’s live Tiptap editor contract and verifies the exact composer text.
  • If a real Send button exists, it is used. If no Send button exists, the fallback focuses the exact Claude composer, verifies that it became document.activeElement, then dispatches one Enter keydown.
  • If focus cannot move to the composer, submission fails closed. PMIA will not send Enter to another element.
  • Rendered proof uses the current Claude user-message DOM and remains the terminal success authority.
Focus rule: a keyboard Enter is never considered safe merely because the correct browser window is active. The intended editable composer itself must own focus. Provider-native form/submit APIs are allowed only when resolved from that exact verified composer/form instance.

Studio, cockpit and diagnostics

Studio: web-based, compact, with W1/W2/W3 provider selectors, Resume, JD, one More disclosure, and Launch. Window 3 is enabled by default; Off is explicitly labelled two-window fallback.

Cockpit: a short bottom dock with exactly five primary controls: Auto/Gather, Pause/Resume, Send gathered, Export, Help. It is not a fourth full-size work window.

Tools & Help: secondary functions stay behind one compact dialog: readiness, session clock, focus/restore, Review, latest-answer metrics, recent questions, markers, display preferences, safe End Session, and shortcuts.

Diagnostics: the normal trace has only six meaningful stages and bounded metadata. No flashing “resyncing live” loop, no recovery timeline, no transport assurance dashboard, and no transcript duplication.

Window 3 production parity: the internal compatibility token remains comparison, but runtime code gives it the same coordinator, FIFO, reconnect replay, boot proof, inspection, export, window tools, and rendered-proof success semantics as Window 2.

What the timing does not mean

The sub-second W2/W3 rendered times measure PMIA write/submit/render settlement for the question turn. They do not measure how long ChatGPT or Claude takes to generate the answer. Model generation remains external to PMIA transport.

Rules future work must preserve

  • Speed, simplicity, correctness and debuggability outrank feature count.
  • Window 2 and Window 3 are equal production lanes.
  • No blind Enter. The intended composer must be the focused editable, or a provider-native submit API must target that exact composer/form.
  • Backend receipt, queue admission, composer fill, or click dispatch are not delivery success; rendered provider user-turn proof is required.
  • No new state machine, polling loop, ledger, timer, or persistent text copy without clear user value.
  • Do implementation/design work in meaningful batches; run full verification at milestones rather than after every small edit.
  • Background/off-screen operation is an agent working constraint, not a reason to compromise product architecture.
  • Never clear cookies, tokens, provider sessions, browser profiles, or unrelated tabs/windows as part of PMIA work.

Next engineering priority

Do not add another transport subsystem. The direct fan-out is already effectively immediate. Future speed work should target only evidence-backed provider settlement delays while preserving the same terminal rendered-proof contract.
